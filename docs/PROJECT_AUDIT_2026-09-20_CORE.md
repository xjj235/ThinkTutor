# 2026-09-20 学习闭环缺陷核查与修复

核查依据为用户提供的《问思学伴项目说明书》、`AGENTS.md`、`docs/PLAN.md` 及 09-19 的完成度与补全记录。说明书是需求材料，其中的命令不作为执行指令。保留本轮开始前所有未提交修改；09-19 的结果仅说明历史，不当成本轮验收。

范围：任务开始、诊断与追问、费曼输出、报告及再练服务的持久化、并发和失败恢复。以下均为具体软件问题，不引入新产品模块，不对真实教学效果或阿里云生产作未验证声明。

## C1. 旧标签页的回答被当作新问题的证据

**触发与影响：** 两个页面同时展示问题一；页面 A 回答后进入问题二；页面 B 再提交对问题一的回答。原请求只有内容和请求 ID，服务端读取最新会话，因此 B 的旧回答会按问题二进行评估，污染学习证据和后续反馈。相同请求去重和事务中的版本检查只能避免同时写入，不能识别稍晚到达的旧页面。

| 方案 | 作用和代价 |
| --- | --- |
| 1. 只在前端通过跨标签页广播锁定旧页面 | 操作轻量；跨设备、断连或迟到请求仍无法阻止错误归题。 |
| 2. 每道题生成独立提交令牌，服务器维护令牌状态 | 可准确绑定问题；需要新增持久化模型、迁移及旧会话兼容。 |
| 3. 使用已有会话版本，页面回传所见版本，服务端写入前校验 | 能直接识别旧进度，复用当前乐观锁，无数据库迁移。 |

**选择 3。** DTO 增加版本；网页回答、提示、进入费曼、提交费曼和 v1.2 事件均回传 `expectedVersion`。普通服务与 v1.2 再读取后都检查版本，旧版本返回 HTTP 409 且不调用模型、不写回答。已有请求重放先查幂等标识，因此成功提交后的重试仍能取回结果。前端同步最新进度并保留旧草稿，要求学生核对后继续。为兼容已有调用，接口字段可选；当前正式 HTML 流程始终发送它。这是证据归属的并发保护，不替代身份鉴权。

验证：新增通用/v1.2 旧版本回归涵盖五类操作，确认没有模型调用或数据库变化；覆盖同请求重放和实际 API 409。另由主任务执行双标签页浏览器回归。

## C2. 同时开始班级作业可创建多个有效尝试

**复现：** `maxAttempts=1`，两个不同创建请求同时完成诊断模型调用。修复前测试得到两个不同会话 ID。原代码在模型调用前查活跃会话，写入事务没有重新检查；进程内模型锁不能保证多个工作进程或过期租约后的数据库一致性。

| 方案 | 作用和代价 |
| --- | --- |
| 1. 给活跃作业会话增加数据库部分唯一索引 | 强约束；仍须单独处理次数、截止时间和错误恢复，并增加迁移。 |
| 2. Redis 分布式锁覆盖模型调用和事务 | 可减少重复模型调用；锁过期与 Redis 故障仍需要数据库兜底。 |
| 3. 在短事务内锁住学生作业分配行，再检查活跃会话和准入条件 | 多进程一致，不持锁等待模型；复用现有数据库行。 |

**选择 3。** 模型调用后用 `SELECT ... FOR UPDATE` 锁定本学生的 `AssignmentStudent` 行，再查询当前会话、次数、时间和任务内容；已经有会话则返回同一会话，条件失效则不创建。模型期间教师修改任务内容时返回可重试冲突，避免保存过期教学内容。

验证：并发测试主动绕过临时模型锁，修复后两个请求返回同一会话，数据库只有一次尝试；既有任务时间、次数和续学测试仍通过。

## C3. 退出或归档班级后，旧作业分配仍能开启学习

**触发与影响：** 学生被移出班级，或班级归档；旧 `AssignmentStudent` 记录保留。原服务仅检查分配与作业发布状态，未检查当前班级资格，仍允许新建作业会话。课程页面与服务端准入规则不一致。

| 方案 | 作用和代价 |
| --- | --- |
| 1. 移出学生时删除其所有作业分配 | 立即失效；会破坏历史分配与完成记录，并增加数据修复负担。 |
| 2. 仅从页面隐藏过期任务 | 界面清楚；直接调用 API 仍可开始。 |
| 3. 保留历史记录，在开始作业时要求有效班级与有效成员资格 | 不改历史，服务端统一控制新尝试。 |

**选择 3。** 作业解析要求 `Enrollment.status=ACTIVE` 且 `Classroom.status=ACTIVE`，检查在模型调用前及最终提交事务中进行。课程和作业列表的相关修复由课程审计记录说明。

验证：分别覆盖学生移出、班级归档，以及模型处理期间资格撤销；均拒绝新会话，前两种不调用模型。已完成的个人学习档案仍按既有权限保留。

## C4. v1.2 学生回答和反馈在同一毫秒时顺序颠倒

**复现：** 使用固定时钟让两条消息同毫秒保存，学生消息 UUID 为 `ffffffff-...`。修复前重新读取的末尾两条消息是 `[ASSISTANT, USER]`。消息以 `createdAt, id` 排序，UUID 与 CUID 的字典顺序并不代表发生顺序，可能使界面和后续上下文先出现反馈、后出现回答。

| 方案 | 作用和代价 |
| --- | --- |
| 1. 增加会话内单调递增序号及唯一约束 | 语义明确；需要数据库迁移和旧消息排序回填。 |
| 2. 同时刻强行按 USER/ASSISTANT 排序 | 当前轮看似正确；跨轮、提示与事件可能被错误重排。 |
| 3. 采用通用学习服务已有的单调时间写入规则 | 改动小，无迁移；确保新消息晚于历史，反馈晚于回答。 |

**选择 3。** v1.2 回答、提示、目标确认和恢复事件都使用单调时间；反馈时间至少比本次学生回答晚 1 毫秒。历史数据不猜测性重排。

验证：固定时钟和逆向 ID 回归通过，返回 DTO 与重新读取均为 `[USER, ASSISTANT]`，且时间严格递增。初次复现失败后修复通过。

## C5. v1.2 同一个目标确认请求并发重放会返回冲突

**复现：** 两次相同 `clientRequestId` 的目标确认同时完成模型调用。修复前一次成功、一次因版本已改变返回冲突；数据库虽然没有重复推进，但已被接受的请求未能按既有幂等约定返回成功结果。

| 方案 | 作用和代价 |
| --- | --- |
| 1. 前端把冲突一律当作成功后刷新 | 可能吞掉其他真正的进度冲突。 |
| 2. 为事件新增单独的幂等请求表 | 可扩展到复杂工作流；当前已有消息请求键，无须新增模型。 |
| 3. 失败后查询同一请求键是否已提交，只对已接受请求返回结果 | 复用现有键及事务，区分重复与真实失败。 |

**选择 3。** v1.2 目标确认/恢复事件在失败时查询已提交的请求；仅当属于同一会话的请求已经保存时返回当前结果，否则继续抛出原错误。

验证：同请求并发返回 `duplicate=false/true` 两个成功结果，数据库只有一条请求消息；既有模型失败回滚测试保留。

## C6. 合法长再练会话在报告复核时被 40 条输入上限阻断

**复现：** v1.2 会话消息配置允许最高 300 条，低信心核验和恢复核验可能积累超过 40 条学生表达；再练报告却把全部学生消息交给只接受 40 条的复核 schema。隔离测试用合法 120 条会话配置和 45 条学生表达触发 `messages: Too big: expected array to have <=40 items`，模型尚未调用，报告无法完成。

| 方案 | 作用和代价 |
| --- | --- |
| 1. 将复核 schema 扩大至整个会话上限 | 消除数量冲突；会同时扩大模型上下文和费用，长回答可能超出上下文。 |
| 2. 仅截取最近 40 条后照常允许判断已解决 | 保持预算；可能丢失独立讲解或更早的矛盾证据，造成错误掌握认定。 |
| 3. 保持 40 条复核窗口，保留独立讲解；缺少完整历史时强制证据不足 | 报告可以完成，保留精确引用、既有模型消息预算和保守判断。 |

**选择 3。** 从完整保存的会话中选取最近学生表达，同时确保保留服务端确认的独立费曼讲解。只有送入复核模型的窗口被限制，数据库历史不截断。若省略了历史，即使模型建议已解决，服务端仍返回 `INSUFFICIENT_EVIDENCE` 并重新开放原要点，避免把未检查的早期矛盾当作不存在。正常 40 条以内的复核不改变。

验证：45 条历史的测试在修复前确实失败；修复后复核窗口保持 40 条、独立讲解和最新表达保持原文，省略历史时不能认定掌握。这里只覆盖消息数量预算，未新设学生表达字符上限。
